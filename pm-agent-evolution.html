  • ✕ 你说「查项目」才去查
  • ✕ 发现异常不会主动说
  • ✕ 不会自己修问题
  • ✕ 不知道自己做得好不好

  • ✓ 每 30 分钟自动巡检 6 项指标
  • ✓ 异常即时写入健康报告
  • ✓ 低风险问题自己修（如重试失败同步）
  • ✓ 每次行动写审计日志，可回溯
  • ✓ 监控自己的健康，坏了能发现

Agent 的四个阶段

每次运行 4 步走，全程耗时不到 5 秒

1

感知 Perceive

检查 6 个信号：sync链路、部署状态、数据可读、项目过期、产出退化、不确定堆积

2

决策 Decide

7 条规则匹配 → 按信任级别过滤 → 冷却期检查 → 生成行动清单

3

行动 Act

执行行动（重试/标记/诊断/日志）→ 每次行动前后写审计记录

4

自检 Self Check

检查自身文件完整性、写入权限、日志大小 → 输出健康报告

NARRATIVE · 为什么这样设计

三条设计原理

不是拍脑袋想的，每条都有明确的原因

🔍

原理一：观察者模式

Agent 不替代任何现有东西——只是在已有的数据流水线上加一双眼睛。

为什么不重写？因为现有系统是你的业务代码，Agent 是你的运维。它们解耦了，Agent 坏了不影响项目数据，数据格式变了 Agent 报错但不会破坏数据。

🪜

原理二：信任阶梯

不是「信任 vs 不信任」的二选一，是一把可以逐级拧开的阀门。

为什么分级？因为信任不是一次给的，是挣来的。Agent 每正确处置 100 次，你就拧开一级。搞砸了就拧回去——不是关掉，是降级。

🪞

原理三：自我指涉

Agent 管理项目，也管理自己——它的代码作为第 21 个项目存在于看板里。

为什么自举？两个好处：1) Agent 崩了不波及其他项目（原理一保证）2) 你看看板能看到 Agent 的表现数据，就像看其他项目一样，不需要专门的监控面板。

⚙️

核心技术：比对而非 AI

Agent 不靠大模型推理。每一行代码都是确定性的——定义正常值 → 读取实际值 → 比对。

为什么不做 AI？因为数据已经是结构化的 JSON，不需要「理解」，只需要「比对」。纯 Python 标准库就够了——json.load() + datetime + requests.head()。
