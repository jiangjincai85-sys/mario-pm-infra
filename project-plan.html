🧠 一句话理解这个方案

现在的项目信息就像堆在抽屉里的发票——每张都有用，但需要的时候你得翻遍所有抽屉才能找到一张。
这个方案要做的事就是：把所有发票按类别贴到一张大表上，上面还标注了"这张发票是从哪个店拿的"（源文件追溯）和"这张发票用了几次报销"（产出追踪）。
以后谁要查，看这张表就行，不用翻抽屉了。

中台三层：一个JSON解决所有问题

第一层 · 源文件追溯 溯源层

  • 记录你给我的每一个 Docs链接、Excel、Word、会议纪要
  • 每条源文件带"关键信息摘要"——一眼就知道这文件讲了什么
  • 记录获取日期——知道数据是否过期
  • 没有这层 → 数据是"无根之木"，不知道信不信
为什么重要：就像发票上的店名和日期，有了它你才能回去验证、更新、补充。别人看到数据，可以追溯到底是从哪个会议纪要里提炼出来的。

第二层 · 结构化字段 内容层

  • decisions[] — 决策日志（你做了什么决定、为什么、什么时候）
  • risks[] — 风险追踪（什么可能出问题、有多大影响、怎么应对）
  • todos[] — 待办清单（要做什么、什么时候做、优先级多高）
  • kpi{} — 核心指标（项目目标是什么、现在进展到哪）
  • 所有项目必须填完这8个字段，空也写[]——绝不允许缺字段
为什么重要：就像超市货架的分区标签——每个类别都在固定位置，找东西不用翻遍整个仓库。

第三层 · 产出追踪 复盘层

  • 项目做完后产出的所有东西（skill、脚本、看板、文档）都记录在这里
  • 每个产出带"使用次数"——知道这个产出有没有人用
  • 每个产出带"使用趋势"——知道是越来越多人用还是没人用了
  • 数据来源是monitor.db——自动统计，不用手动数
为什么重要：项目做完不是终点。产出用了多少次，才是判断"这个项目值不值"的依据。用得少→优化门槛；用得多→重点迭代。

关键设计决策

JSON 是主真相源，.md 是衍生品

  • AI 写入 JSON → 脚本自动生成 .md（人类可读）→ Git追踪变化
  • 为什么：JSON结构固定，追加字段不用拼接Markdown表格
  • 为什么：.md由JSON生成，格式永远一致，不会出现表格格式混乱
  • 任何skill读JSON比解析.md快100倍

上游写入协议：信息一出现就沉淀

  • 你给了一个Docs链接 → 写入 source_materials[] + 提取内容到对应字段
  • 你说"本周要发邮件" → 写入 todos[] + 更新 last_updated
  • 你说"企微客服卡点" → 写入 risks[]
  • 你说"费用科目统一" → 写入 decisions[]
  • 信息不再随会话结束丢失

❓ 不确定标记 + 每晚10点日清

🧠 一句话理解

项目信息里有些东西是确定的（比如"AI创想家5月18日准出"），有些是不确定的（比如"特效师挂账5/22前发邮件"——时间可能推迟、业务方还没确认）。
不确定的标记出来，每天晚上10点我给你一份清单，你来确认或推翻。如果当天没有不确定的内容，我也会告诉你"没有"。

不确定标记（uncertain_items） 标记层

  • type — 不确定的类别：data（数据不确定）| decision（决策未定）| source（来源未验证）| kpi（指标待确认）| todo（时间可能变）
  • content — 不确定的具体内容
  • reason — 为什么不确定
  • flagged_at — 标记日期
  • status — 待确认 | 已确认 | 已推翻
为什么重要：项目中有很多"可能"的信息。不标记→假消息当成真消息用→出错。标记→你每天确认→信息越来越准确。

每晚10点日清 定时任务

  • ⏰ 每天晚上22:00自动执行
  • 扫描所有项目的 uncertain_items → 输出"待确认事项"
  • 扫描所有项目的 todos → 输出"今明两天到期的紧急待办"
  • 扫描所有项目的 risks → 输出"🔴高风险事项"
  • 扫描超过3天没更新的项目 → 输出"⚠️数据可能过期"
  • 如果什么都没有 → 输出"✅ 今天没有需要清理的内容"
这就是"日清"——每天睡前扫一遍，把不确定的确认掉、把紧急的提醒掉、把过期的更新掉。日清日结，信息永远干净。
